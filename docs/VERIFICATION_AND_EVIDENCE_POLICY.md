# Verification and evidence policy

Use VERIFIED only for the exact behavior, source version, environment and criteria supported by a recorded check. IMPLEMENTED means code exists. REPORTED means a claim is retained but not reproduced for the relevant source state. UNKNOWN means evidence is insufficient. NOT_EVALUATED applies to metrics without a valid protocol/data/prediction record. A test count is operational evidence only.

Every major milestone must bind its input archive, changed-source hashes or real Git commit, branch availability, commands, exit/results, test XML/logs, environment/dependencies, failure records, limitations and next tasks. Store original logs and failures. A later check may supersede a current status without deleting the earlier result. No saved artifact may be silently rewritten to make a fingerprint or score pass.

Evidence types remain distinct: exact source quotation, parsed syntax fact, deterministic rule observation, graph candidate, retrieved evidence, model interpretation, caller attestation, independent semantic judgment and frozen evaluation result. A valid quote or content hash establishes correspondence, not entailment. A typed graph path establishes a recorded candidate relationship, not causal impact. Absence in a partial source map or unlinked artifact list is never a negative label.

All material observations retain repository/parser identity, exact revision/role, artifact/hash/span, method, original record ID and available provenance/uncertainty. Fresh source validation occurs before partial report/source delivery. Failed validation clears selectable/displayed stale source. Report exports retain original unknowns and denominators. No reviewed obligation means no MISSING_TEST conclusion.

Author-written fixtures and source-backed engineering audits are development evidence. They cannot become independent labels or final gold. Real reviewer forms remain blank until actual reviewers supply judgments. Do not authenticate reviewer independence from a self-entered name, source hash or successful schema validation. Preserve disagreements, unknown regions and adjudication history.

Keep TEBench source-only inputs, checksum-pinned reference/gold separation, all 314 cases, original failures, separate recovery cache/results and training-only bandit comparison intact. Reuse completed runs by exact resume fingerprint. Record negative results. Do not infer complete impact/consistency gold from a bug-fix patch. Do not repeatedly inspect or optimize against frozen final labels.

No subject scripts, model-generated code, untrusted instructions or repository prompts may execute in the application process. Model/provider calls require explicit allowed configuration, available free local resources and per-run call budgets; no paid fallback. Never claim full-weight RL, Windows/GPU execution, security certification or submission without actual records.

Source-only REA inspection must pin commit/tree, retain licence/provenance, record exact source lines and check captured Git blobs. Mark runtime/tests NOT_RUN when not executed. VIGILANT analogues and test fixtures cannot certify REA runtime behavior or complete parity.

The handoff must always distinguish Completed (exact work verified), Pending (application/research acceptance still open) and Not evaluated (unsupported metrics). Never report unsaved, removed workspace outputs as recovered measurements.
